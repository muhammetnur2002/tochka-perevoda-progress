# Архитектура

## Компоненты

```
 Клиент (браузер)        Telegram (бот + Mini App)         Сотрудники
   │  сайт /, /calculator     │ /tg (webview)  │ бот           │ /admin, /workspace
   ▼                          ▼                ▼               ▼
 ┌──────────────────────── Next.js 14 (один контейнер) ──────────────────────────┐
 │ Server Components ── читают БД под сессией пользователя (RLS)                  │
 │ Server Actions    ── мутации CRM и кабинета переводчика                       │
 │ /api/*            ── REST: заказы, загрузка, платежи, чат, вебхуки, cron      │
 │ middleware        ── обновление сессии Supabase, защита /account /admin ...   │
 └───────┬──────────────────────┬──────────────────────────┬────────────────────┘
         │ supabase-js (anon/JWT)│ service_role (сервер)    │ fetch
         ▼                       ▼                          ▼
   Supabase: Postgres + RLS, Auth, Storage (order-files), Realtime   ЮKassa, SMS.ru, SMTP, Bot API
```

## Принципы

- **RLS — единственный источник правды по доступу.** Приложение ходит в БД под
  JWT пользователя; `service_role` используется только там, где действует
  сервер (создание заказа гостем, вебхуки, cron, уведомления), и всегда после
  собственной проверки прав.
- **Цена считается только на сервере.** Клиент показывает предварительный
  расчёт тем же модулем `src/lib/services/pricing.ts`, но в заказ записывается
  серверный расчёт по ценам из БД; триггер `recalc_order_totals` пересчитывает
  итог по той же формуле (сверяется тестом `pricing_check.sql`). Вставка
  заказов напрямую клиентом запрещена RLS.
- **Гость без регистрации** получает HMAC-токен заказа (24 ч) — им подтверждает
  загрузку файлов и оплату. Знание UUID заказа доступа не даёт.
- **Привязка гостевых заказов** к аккаунту — только после подтверждения телефона
  (SMS-код или контакт Telegram), иначе любой указал бы чужой номер.
- **Внешние провайдеры за интерфейсами** с mock-реализациями: `PaymentProvider`,
  `StorageAdapter` (Supabase / Yandex Object Storage), отправщики уведомлений, `AiProvider`.
- **Время** — производственный календарь по Москве (UTC+3), дедлайн 19:00 МСК,
  праздники в `settings.holidays`.

## Потоки

**Заказ на сайте:** калькулятор (корзина в localStorage) → `POST /api/orders`
(Zod, рейт-лимит, цена из БД, согласие 152-ФЗ с IP/UA) → `POST /api/upload` с
токеном → `/checkout/pay/[id]` → `POST /api/payments` (QR СБП или redirect ЮKassa)
→ вебхук ЮKassa → `payments.status = succeeded` → триггер переводит заказ в
`confirmed` → уведомление клиенту, Realtime-алерт и Telegram менеджерам.

**Mini App:** `/tg` ждёт `Telegram.WebApp`, отправляет `initData` в
`/api/telegram/auth` (HMAC-проверка + свежесть `auth_date`) → сессия Supabase в
cookie → дальше те же API, что у сайта, под RLS клиента.

**Канбан:** `/api/orders` + Realtime-подписка на `orders`; перетаскивание
(dnd-kit) → `PATCH /api/orders/[id]` → RPC `change_order_status` (комментарий в
историю) → уведомление клиента по цепочке Telegram → SMS → email.

## Безопасность (кратко)

CSP (+ `frame-ancestors` для Telegram), HSTS, Referrer-Policy, Permissions-Policy;
приватный бакет и подписанные ссылки на 5 минут; проверка сигнатур файлов при
загрузке; IP-allowlist и перезапрос платежа у ЮKassa; секрет вебхука Telegram;
cron по Bearer-секрету; рейт-лимиты в БД; аудит изменений триггером; защита от
повышения роли и подмены Telegram-привязки триггером. Подробнее — `152-FZ.md`.
